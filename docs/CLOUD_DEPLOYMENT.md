# 第12组：云端部署准备

这份准备把当前本地模块接向同一套云端服务，没有创建服务器、公开端口、上传代码或发送真实短信/邮件。最终仍需结合云服务商、域名和证书实际部署验收。

## 当前可迁移的基础

账号、角色、班级授权、游戏存档、成绩、验证码挑战、会话和限流都在PostgreSQL，多个应用进程共享数据库；浏览器不保存身份令牌或权威存档。前端请求使用同站相对路径，因此换为正式HTTPS域名无需逐项修改API地址。固定用户ID及增量迁移可继续使用，题库旧版本须随代码一起保留。所有应用实例须使用一致的代码、题库发布和密钥配置，共享同一数据库；不要让不同存档结构的程序版本无计划地交替处理同一玩家。

开发内存发送器是测试工具，不能作为云端消息服务。生产仍强制禁用它；实际短信/邮件供应商须实现发送适配契约并另行验收，不应通过公开接口读取验证码。

## 独立生产配置

使用 `config.production`，真实配置由服务器环境变量或受限的进程管理配置注入；字段参考仓库根目录 `.env.production.example`。应用不会自动读取名为.env.production的文件，部署工具必须加载环境变量。原config.settings仍用于本地开发，不能把其直接当成生产配置。

- 明确DJANGO_DEBUG=false、足够随机的独立密钥、具体ALLOWED_HOSTS、无路径的HTTPS PRODUCTION_SITE_ORIGIN。不要上传现有.env、数据库目录或虚拟环境；在服务器重新安装锁定依赖。
- 强制HTTPS跳转、安全Cookie及HSTS（默认3600秒）。子域HSTS与预加载暂不启用，必须先核对域名及所有子域HTTPS情况，框架因此可能仍给出这两项策略警告；不意味着已通过实际部署验收。
- 默认不信任X-Forwarded-Proto。只有应用端口被隔离、可信代理始终覆盖该请求头时，才设置TRUST_HTTPS_PROXY=true；不要在公网直达应用时启用。USE_X_FORWARDED_HOST始终关闭。
- 数据库强制sslmode=verify-full，DB_SSLROOTCERT为服务器内可读取的CA证书绝对路径。DB_HOST必须匹配服务端证书名称，不能随便换成IP；证书文件存在只证明配置齐全，是否能TLS连接须在云端实测。当前生产模板不支持无TLS数据库，若最终采用其他网络部署方式需显式评审。
- DB_CONN_MAX_AGE默认60秒并启用连接健康检查。每个进程/线程可能占数据库连接，须按工作进程和云数据库连接上限配置，不据此宣称支持100人并发。

部署中的真实客户端IP必须由受信任代理及应用服务器正确传入REMOTE_ADDR。应用不会直接相信任意X-Forwarded-For。若所有人都显示代理地址，会共用IP限流；必须在最终服务器链路验证后再开放班级使用，不能简单信任浏览器传来的转发头。

## 发布顺序与检查

1. 确定同一HTTPS站点、应用服务器和PostgreSQL服务，准备数据库普通角色、TLS证书与秘密。服务器运行WSGI/ASGI生产进程，由进程管理器负责重启；本地runserver启动脚本不用于生产。具体进程服务器及反向代理配置待平台确定后编写，不猜测固定主机路径或端口。
2. 对已有数据先备份，并在独立环境演练恢复。迁移本地数据时使用数据库逻辑备份/恢复，保留UUID及全部业务表；不要直接复制Windows的.local数据库目录到云服务器。
3. 在受控环境安装requirements.txt，注入配置，使用 `manage.py check --deploy --settings=config.production`、`check_db --settings=config.production` 核对配置及数据库，再执行 `migrate --noinput --settings=config.production`、`init_roles --settings=config.production`。不能通过删表/迁移文件来修复升级问题。
4. `collectstatic --noinput --settings=config.production` 产生staticfiles，由前置静态服务提供/static/，Django生产进程不负责开发静态文件。不要把应用源码目录直接公开成静态站点。
5. 启动新版本后执行 `migrate --check --settings=config.production`，核对健康入口与真实登录→存档→提交→教师可见，再进行容量和浏览器矩阵验收。迁移和新旧程序共存策略需依实际发布方式决定，不声称零停机升级。

正式域名是浏览器的新来源，本机Cookie不会自动搬到云端，玩家应重新登录。密码摘要和固定ID可保留；密钥轮换会使旧会话及未完成的恢复/验证码凭据失效，要明确通知重新登录/申请，不能因此覆盖个人数据。备份与环境秘密分别保管，Git只保存代码与非秘密模板。

## 健康探测

- GET/HEAD `/health/live/`：仅进程存活，不检查数据库。数据库维护时不要因这个接口成功就认为业务可用。
- GET/HEAD `/health/ready/`：执行只读SELECT 1，数据库不可用返回503及固定unavailable，无连接凭据或异常原文；正常200，禁止缓存。它不检查迁移、题库完整性、容量或依赖供应商，发布时另跑上述命令及业务验收。
- 两者仅用于探测，不公开管理权限。生产HTTP默认跳转HTTPS，负载均衡器须通过正确的HTTPS/可信代理链路探测，不能为了健康探测取消安全跳转。

## 验证码数据保留与清理

新增受信任终端命令 `manage.py prune_contact_challenges`，默认只显示符合条件的数量，不输出地址或验证码，不执行删除。默认仅处理已过期超过1天的挑战，近期过期与未到期记录保留。此一天是原型默认值，实际隐私保留期须在上线前确定。

核对预览后加 `--execute` 才执行；可配置 `--retention-days 1`（1—365）、`--batch-size 200`（1—1000）、`--max-batches 10`（1—1000）。每批独立事务并跳过其他事务锁定行；上限和锁定记录留待后续运行，可重复执行。已验证联系方式、用户、成绩和维护审计不在删除范围。清理是不可恢复的记录删除，应由具备数据库维护权限的部署任务调用，普通用户无网页入口。

云端可由平台定时任务调用该命令，加 `--settings=config.production`；本轮没有创建定时任务，也没有清理真实库。已有 `clearsessions` 与 `prune_rate_limits` 可作为其他维护任务，但其具体资源消耗和执行频率仍需在部署环境评估。
